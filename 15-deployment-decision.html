Decision · one useful mental model

What does a successful task really cost?

A cheaper model call fails twice as often. Is it still the cheaper way to answer the user?

About 8 minutes · optional lab takes additional time

Try the interactive experiment ↓

A backend supplies model responses. Hosted means using a provider’s service; self-hosted means operating the model on infrastructure you control. A model call is one request to that backend.

Attempt: one submitted application task.

Success criterion: the observable conditions a task must meet.

Operating cost: cost of keeping the service available and maintained.

Cost per success: total relevant cost divided by successful tasks; lower is better.

What you need from before · recall the previous model

Does smaller raw weight data establish a faster or equally accurate model?

No. Measure supported execution and task quality separately.

Predict first: One backend costs half as much per attempt but succeeds only one quarter as often. Is its cost per successful task lower?

No. Holding other costs equal, dividing by the lower success rate makes its successful tasks more expensive.

Define success before comparing prices

Our document assistant succeeds when it answers the requested question, cites supporting evidence, and handles missing evidence explicitly. A response that merely arrives without an error does not meet that standard. Add an acceptable latency requirement if the product needs one, then use the same requirement for every backend.

Build a small fixed evaluation set with known source passages. Include answerable, unsupported, conflicting, and tool-failure cases. Keep expected behavior separate from generated responses. Human review can establish a useful initial score; automated checks should inspect observable requirements rather than rewarding fluent wording.

A hosted bill usually varies with usage and the provider’s accounting. A self-hosted service can incur rental cost while idle. Both can incur retries and application maintenance. Include the costs relevant to your decision period and record what you leave out. Current prices must be checked when making an actual purchase.

Compare viable options under a stated workload

The demo uses invented currency units, not provider quotes. It computes hosted cost as attempts multiplied by cost per attempt. It computes self-hosted cost as hourly rental multiplied by operating hours, plus a chosen operating allowance. Each is divided by the number of successful tasks. With zero successes, that unit cost is undefined, not zero, even when the period’s bill is known.

The volume slider changes cost allocation, not server capacity. A low calculated unit cost does not establish that the rented hardware can process that volume within its hours or latency target. Bring the measurements from lessons 12 and 13 into the decision. Exclude an option that cannot meet quality or service requirements, even if its arithmetic looks attractive.

Your final output is a short decision record. State the workload, evaluation score, latency observations, total cost basis, and unresolved assumptions. A hybrid design can route some tasks to a small local model and harder cases to a hosted model. Evaluate routing failures and the extra control logic rather than assuming a hybrid is automatically better.

Two ways to picture it

This resembles measuring the cost of completed jobs rather than raw API requests. A failed task may still incur costs, and retries complicate the denominator.

It also resembles comparing transport by delivered parcels rather than vehicle fuel price. Delivery quality matters, but that analogy cannot price data governance or model maintenance.

Work it out

Assume 1,000 attempts. Hosted cost is 0.02 units per attempt and 90% succeed: 20 ÷ 900 ≈ 0.022 units per success. A self-hosted period costs 58 units and 80% succeed: 58 ÷ 800 = 0.0725. These are invented inputs.

Illustrative arithmetic: stated assumptions, not measurements.

Hands-on milestone · run in your own lab

Apply it to the document assistant

  1. Freeze 20 representative document tasks and define supported, unsupported, and failure outcomes.
  2. Run the same tasks through your hosted and self-hosted adapters. Keep source versions fixed.
  3. Record quality, latency distribution, failures, total relevant cost, and operating assumptions.
  4. Write a one-page deployment decision. Name what evidence would make you change it.

Done when: You can choose a deployment from recorded application outcomes and stated assumptions, rather than model popularity or token price alone.

Can you use the idea elsewhere?

A self-hosted calculator becomes cheaper at high volume. What still needs verification?

Hardware capacity, quality, latency, reliability, and the completeness of the cost assumptions.

A response passes JSON validation but cites the wrong document. Is it a successful task?

No. Output structure and evidential correctness are separate criteria.

A hosted model improves after your evaluation. Does the old comparison establish current superiority?

No. Record model versions and refresh the comparison when relevant behavior changes.
