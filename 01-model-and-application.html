Application: your program, which receives requests and controls real operations.

1. One request, three responsibilities

Imagine you ask: “How long do customers have to return a purchase?” Your policy document contains the answer.

The model cannot search that document through a function your program has not connected. It can request a connected tool.

Here, a hosted model runs at a provider. Your application sends it a request over the network.

The application sends context and the available tool descriptions to the model. The model can return a structured tool request.

The application checks that request. If allowed, it calls the tool and sends the returned passage to the model.

The model can then compose an answer using that passage. Your application displays the answer.

Read in docs · Application-owned tool use

The important boundary is between proposing and executing. Crossing it needs real software, with access to the operation.

2. Change one condition

Two applications can receive the same proposed call and handle it differently. One allows document access; the other blocks it.

Return to the demo and press Block search and restart. Predict whether the document tool will execute.

A capable model still needs an application that connects the right operation. A detailed request does not create that connection.

Think of a colleague asking, “Please open the policy.” The request is useful, but someone still needs to open it.

That analogy stops at the boundary. A model response does not establish a colleague’s identity, access, or accountability.

As a developer, compare a tool request with a function call description in a message. Data names an operation; a receiver dispatches it.

This analogy also has a limit. Model-produced arguments can be unsuitable even when their format is valid.

In your future app, the receiver must check both the requested operation and its arguments. We will build that check later.

3. Count the work before you build

You have seen each component’s job. Now count the work required for one successful answer in this example.

Predict: how many model calls and tool executions does that path require?

Two model calls and one tool execution. The tool result is new context for the second model call. This is our example, not a universal count.

Here is a worked timing example. Suppose each model call takes two seconds and the document tool takes one second.

The calls happen one after another. The total is 2 + 1 + 2 = five seconds, ignoring other overhead.

Now change just one feature: the document tool takes four seconds. The model calls still take two seconds each.

A proposed tool call changes the world only when an application executes it.

Try the idea on a new case

1. The model says “Draft saved,” but your application executed no save operation. What do you know?

You know it generated those words. The statement alone does not establish that a draft exists. Check the application’s operation record or the saved file.

2. You replace the model with a different model. Must you replace the document search function too?

No. Your application owns that function. It can keep the same search operation, although a new model may need a different connection or message format.

3. The tool returns a timeout. Should the application present an answer as verified against that document?

No. This attempt supplied no document evidence. The application needs an explicit failure path or a controlled second attempt.
