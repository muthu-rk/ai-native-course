An agent is the model-and-tool process carrying out a task. Its runtime coordinates those steps; the model produces responses within them.

Gateway: the long-lived OpenClaw service that accepts connected clients.

Channel: a surface through which messages arrive.

Session: a distinct conversation and its associated state.

Workspace: the files and instructions assigned to an agent.

The loop is only one part of a product

A command-line loop starts when you run it. A persistent assistant must receive messages, find the relevant conversation, locate the agent’s working context, and deliver a response. Those responsibilities are visible even before you inspect model generation.

Current OpenClaw documentation describes a long-lived Gateway and an integrated embedded agent runtime. It also describes per-agent workspaces and session storage. Study this as its own system rather than assuming it wraps today’s Pi implementation. A similarity in concepts does not establish a current code dependency.

Follow one document question from the local Control UI to its session and workspace. The Control UI is the browser interface used to operate the assistant. Ask which stored information returns after a restart and which connection must be re-established. A working browser window alone does not establish durable recovery.

Make boundaries concrete

The demo routes two invented messages. You can choose a separate session key for each sender or deliberately use a shared key. The shared case combines their recorded contexts. It illustrates the risk of a careless application mapping; it does not claim that OpenClaw uses this simplistic rule.

An agent can have a workspace and still need caller-specific permissions. Session separation prevents one kind of accidental mixture, but it is not the same as authorization. Keep that distinction from lesson 3. First trace a harmless read using the local interface, then investigate other channels only when the application needs them.

The useful comparison is now three-way: your small harness, Pi’s reusable runtime, and OpenClaw’s integrated assistant. For each, identify who owns routing, model calls, storage, and delivery. Choosing a complete assistant system is a product decision; it does not require changing the underlying document evidence task.

Two ways to picture it

A Gateway resembles an application server accepting connections and routing requests. The analogy does not establish that every message has ordinary HTTP semantics.

A session resembles a separate notebook for each conversation. A notebook boundary helps organization, but it does not itself enforce digital permissions.

Work it out

Two sessions contain three messages each. That is six messages stored across two histories. A request for one session should select its own three, not all six.

Hands-on milestone · run in your own lab

Apply it to the document assistant

  1. Follow current OpenClaw setup in a dedicated test workspace. Record the version and configured agent ID.
  2. Run the commands below with two distinct session IDs. If named-session creation is unsupported, update the Gateway first.
  3. List sessions as JSON; match both IDs to their agent. Inspect each session in the local dashboard.
  4. Record session ID, agent, workspace path, model, and any tool observations in a small table. Repeat the listing after a controlled restart.
Worked code or commands
# After setup; AGENT_ID means a configured test agent, not a model name.
openclaw --version
openclaw gateway status
openclaw agent --agent AGENT_ID --session-id course-a --message "Remember: policy A says 30 days." --json
openclaw agent --agent AGENT_ID --session-id course-b --message "Remember: policy B says 14 days." --json
openclaw sessions --all-agents --json
openclaw dashboard

Can you use the idea elsewhere?

Two conversations use separate sessions. Does that authorize both to read the same confidential file?

No. Session identity and document authorization are separate controls.

You replace the model provider. Which surrounding responsibilities still exist?

Routing, session state, workspace selection, tool checks, and response delivery.

A restarted UI shows the old conversation. Does that prove every tool effect was recovered?

No. Inspect the operation records and uncertain outcomes separately.
